# Requirements Document

## Introduction

Perfil Crediticio is a Generative AI + RAG conversational assistant for Wayni users. It explains how the risk engine evaluates them, what factors block their credit access, and what concrete actions they can take to improve their situation. The system integrates with Wayni's existing credit decision flow and surfaces explanations post-decision and from the home screen.

## Requirements

### R1 — Mostrar cómo Wayni evalúa al usuario

**User Story:** As a Wayni user, I want to understand how the risk engine evaluated my loan application, so that I am not left confused after a credit decision.

#### Acceptance Criteria

1. GIVEN a user views their Perfil Crediticio WHEN the profile loads THEN the system SHALL display a natural-language explanation of how Wayni evaluated them, generated by Amazon Bedrock (Claude Sonnet 5.5) using the `rejection_variable` and primary factors from DynamoDB.
2. GIVEN a pre-calculated explanation is stored in DynamoDB WHEN the user requests their profile THEN the system SHALL return that cached explanation without invoking Bedrock again (sub-second response).
3. GIVEN no cached explanation exists WHEN the user requests their profile THEN Lambda `GenerateProfileExplanation` SHALL invoke Bedrock and store the result in DynamoDB before returning it.

---

### R2 — Explicar qué factores bloquean acceso a crédito

**User Story:** As a Wayni user who was denied credit, I want to know which specific factors blocked my access, so that I understand what is holding me back.

#### Acceptance Criteria

1. GIVEN a credit decision exists for the user WHEN the profile loads THEN the system SHALL display the 2–3 primary factors that most impacted the evaluation, sourced from the `primary_factors` field in DynamoDB.
2. GIVEN a factor is displayed WHEN Bedrock generates the explanation THEN each factor SHALL be described in plain language (no internal codes or jargon) that a non-expert can understand.
3. GIVEN factors are displayed WHEN the explanation is rendered THEN the system SHALL NOT promise or imply that addressing a factor guarantees future approval (enforced via Bedrock Guardrails).

---

### R3 — Sugerir acciones concretas para mejorar situación crediticia

**User Story:** As a Wayni user, I want to receive concrete, actionable suggestions to improve my credit situation, so that I know exactly what steps I can take.

#### Acceptance Criteria

1. GIVEN a user views their Perfil Crediticio WHEN actionables are available THEN the system SHALL display actionable suggestions sourced from the `actionables` field in DynamoDB, explained in natural language by Bedrock.
2. GIVEN an actionable has a direct causal effect on the credit score WHEN it is displayed THEN the system SHALL clearly label it as a direct-effect action (e.g., "Paying this debt on time will directly improve your profile").
3. GIVEN an actionable has no directly attributable effect WHEN it is displayed THEN the system SHALL use hedged language (e.g., "This may help improve your profile over time") and Bedrock Guardrails SHALL block any promise of guaranteed improvement.
4. GIVEN Lambda `CalculateRetryDate` has computed a suggested retry date WHEN actionables are displayed THEN the system SHALL show that estimated date alongside direct-effect actionables.

---

### R4 — Perfil accesible después de solicitud de préstamo y desde home

**User Story:** As a Wayni user, I want to be able to access my credit profile at any time from the home screen or immediately after a loan application, so that I am never blocked from seeing my status.

#### Acceptance Criteria

1. GIVEN the risk engine emits a `credit_decision_made` event WHEN EventBridge receives it THEN Lambda `GenerateProfileExplanation` SHALL be invoked asynchronously to pre-calculate and store the explanation in DynamoDB before the user navigates to their profile.
2. GIVEN a user navigates to their credit profile from the Wayni home screen WHEN the GET `/user/{user_id}/credit-profile` endpoint is called THEN the system SHALL return a response within 3 seconds under normal load.
3. GIVEN a user has no prior credit decision WHEN they access their profile THEN the system SHALL return an appropriate empty-state response (not an error).

---

### R5 — Mostrar estado de línea, nivel de perfil, 2-3 factores principales

**User Story:** As a Wayni user, I want a clear summary view of my credit line status, profile level, and top factors, so that I can quickly grasp where I stand.

#### Acceptance Criteria

1. GIVEN the `user_credit_profile` DynamoDB table contains a record for the user WHEN the profile is fetched THEN the response SHALL include `line_status`, `profile_level`, and `primary_factors` (2–3 items).
2. GIVEN the BCRA data used for the evaluation has a known cutoff date WHEN the profile is displayed THEN the system SHALL surface the `bcra_cutoff_date` with a note explaining the 1–2 month data lag (R16).
3. GIVEN any of the three fields (`line_status`, `profile_level`, `primary_factors`) is missing in DynamoDB WHEN the profile is fetched THEN Lambda SHALL return a graceful partial response indicating which data is unavailable, not a 500 error.

---

### R6 — Asistente conversacional para preguntas sobre el perfil

**User Story:** As a Wayni user, I want to ask questions about my credit profile in natural language and get clear answers, so that I can understand my situation without calling support.

#### Acceptance Criteria

1. GIVEN a user sends a question via `POST /user/{user_id}/ask` WHEN the question is within scope (about the user's own credit profile) THEN Bedrock AgentCore SHALL route it to Lambda `ProcessConversationalQuery`, which consults DynamoDB and returns a Bedrock-generated answer.
2. GIVEN Bedrock AgentCore processes a question WHEN the response is being streamed THEN the system SHALL support Bedrock streaming to improve perceived latency (response starts appearing in < 1 second).
3. GIVEN a user sends the same question multiple times WHEN conversation history is available THEN AgentCore SHALL maintain session context so the user does not have to repeat themselves.
4. GIVEN a response is generated WHEN it is returned to the user THEN Bedrock Guardrails SHALL have been applied to ensure no guaranteed credit promises are made.

---

### R7 — Derivar preguntas fuera de alcance a soporte

**User Story:** As a Wayni user, I want the assistant to recognize when it cannot answer my question and connect me to a human, so that I am never left without help.

#### Acceptance Criteria

1. GIVEN a user asks a question outside the scope of their credit profile (e.g., general banking, account issues) WHEN AgentCore evaluates it THEN the system SHALL detect it as out-of-scope and invoke Lambda `DeriveToSupport`.
2. GIVEN `DeriveToSupport` is triggered WHEN it executes THEN it SHALL create a support ticket in the CX system (e.g., Zendesk) with the user ID and the out-of-scope question as context.
3. GIVEN a question is escalated to support WHEN the user receives the response THEN the assistant SHALL communicate clearly that the question has been forwarded and provide an estimated response time if available.

---

### R8 — Flujo de reclamo para datos incorrectos

**User Story:** As a Wayni user, I want to dispute data I believe is incorrect in my credit evaluation, so that errors don't unfairly block my access to credit.

#### Acceptance Criteria

1. GIVEN a user initiates a dispute via `POST /user/{user_id}/dispute` WHEN Lambda `HandleDisputeFlow` executes THEN it SHALL consult DynamoDB to identify the disputed data point and retrieve the relevant dispute guide from S3.
2. GIVEN the dispute guide is retrieved WHEN the response is returned THEN it SHALL include the steps, links, and contact information for the appropriate reporting entity (BCRA, bank, etc.) based on the dispute type.
3. GIVEN a dispute is initiated WHEN `HandleDisputeFlow` completes THEN it SHALL log the dispute event in DynamoDB as an audit trail entry (user ID, timestamp, disputed field, guide served).
4. GIVEN a dispute is logged WHEN an audit is performed THEN the log SHALL NOT contain any PII beyond the user ID.

---

### R9 — Sugerir fecha de reintento basada en accionables

**User Story:** As a Wayni user who was denied credit, I want to know when I should retry my application after taking corrective actions, so that I don't waste a credit inquiry too early.

#### Acceptance Criteria

1. GIVEN a user has at least one direct-effect actionable WHEN Lambda `CalculateRetryDate` runs THEN it SHALL compute a suggested retry date based on the expected resolution time of the actionable (e.g., payment reporting window, BCRA update cycle).
2. GIVEN the retry date is calculated WHEN it is stored THEN it SHALL be persisted in the `user_credit_profile` DynamoDB record under a `suggested_retry_date` field.
3. GIVEN a user views their profile WHEN a suggested retry date exists THEN the system SHALL display it alongside the relevant actionable in the explanation.

---

### R10 — Mapear 8 estados del motor a 4 narrativas

**User Story:** As a product owner, I want the system to map the 8 internal risk engine states to 4 user-friendly narratives, so that communication is consistent and legally reviewed.

#### Acceptance Criteria

1. GIVEN a credit decision has a `decision_state` value WHEN Lambda `GenerateProfileExplanation` executes THEN it SHALL select one of the 4 narrative templates from S3 based on the state mapping table.
2. GIVEN the 4 narrative templates are stored in S3 WHEN a new version is uploaded THEN the system SHALL use the latest version on the next invocation (no Lambda redeployment required).
3. GIVEN the 4 narratives are: "Tenés línea y podés hacerla crecer", "Podés destrabar tu línea", and the two rejection narratives WHEN any of them is rendered THEN it SHALL have been reviewed and approved by Legal before production deployment.
4. GIVEN a `decision_state` does not match any of the 8 known states WHEN the mapping is attempted THEN Lambda SHALL return a safe fallback narrative and log the unknown state to CloudWatch.

---

### R11 — Distinguir accionables de efecto directo vs. sin efecto atribuible

**User Story:** As a Wayni user, I want to know which of my suggested actions will directly improve my credit profile versus which ones only might help, so that I can prioritize the right actions.

#### Acceptance Criteria

1. GIVEN a list of actionables is computed for the user WHEN they are stored in DynamoDB THEN each actionable SHALL have an `effect_type` field set to either `direct` or `indirect`.
2. GIVEN actionables are displayed WHEN the explanation is generated by Bedrock THEN direct-effect actionables SHALL be presented with more prominent language than indirect ones.
3. GIVEN an `indirect` actionable is included in the explanation WHEN Bedrock generates the text THEN Guardrails SHALL block any wording that overstates its impact.

---

### R12 — Legal valida que explicaciones no prometan resultados no garantizables

**User Story:** As a legal/compliance officer, I want the system to enforce constraints on what the AI can say, so that Wayni is not exposed to regulatory risk from unverifiable promises.

#### Acceptance Criteria

1. GIVEN Bedrock is invoked for any explanation or conversational response WHEN the response is generated THEN Bedrock Guardrails SHALL be applied with rules that block phrases that promise guaranteed future credit approval.
2. GIVEN a Guardrails policy is active WHEN it blocks a generated response THEN the system SHALL substitute a safe fallback explanation and log the blocked content (without PII) to CloudWatch.
3. GIVEN Legal has approved the Guardrails ruleset WHEN it is deployed to production THEN any changes to the ruleset SHALL require a new Legal approval cycle before deployment.

---

### R13 — Reducir consultas de soporte por rechazo

**User Story:** As a Wayni operations manager, I want the credit profile assistant to reduce inbound support contacts about credit rejections, so that support costs go down.

#### Acceptance Criteria

1. GIVEN the conversational assistant is live WHEN a user asks a question typically handled by support (e.g., "why was I rejected?", "what is BCRA?") THEN the assistant SHALL answer it without requiring human intervention.
2. GIVEN the assistant is live WHEN CloudWatch metrics are collected THEN the system SHALL track `support_deflection_rate` (questions answered by assistant / total questions asked) as a custom metric.
3. GIVEN a CloudWatch alarm is configured WHEN `support_deflection_rate` drops below 70% THEN an alert SHALL be sent to the operations team.

---

### R14 — Motor registra rejection_variable para cada evaluación (assumption)

**User Story:** As a system integrator, I want the risk engine to record the `rejection_variable` for every evaluation, so that the credit profile system has the data it needs to generate explanations.

#### Acceptance Criteria

1. GIVEN the risk engine emits a `credit_decision_made` event to EventBridge WHEN the event payload is validated THEN it SHALL contain a non-null `rejection_variable` field.
2. GIVEN the event lacks `rejection_variable` WHEN Lambda `GenerateProfileExplanation` receives it THEN the function SHALL log a warning to CloudWatch and generate a generic explanation that does not reference a specific rejection variable.

> **Assumption**: The risk engine already records `rejection_variable` per evaluation. This must be confirmed with the risk engine team before production deployment.

---

### R15 — Integración con motor de riesgos para datos de evaluación

**User Story:** As a system architect, I want the credit profile service to receive credit decision data from the risk engine via events, so that the two systems remain decoupled.

#### Acceptance Criteria

1. GIVEN the risk engine emits a `credit_decision_made` EventBridge event WHEN EventBridge receives it THEN the event SHALL trigger Lambda `GenerateProfileExplanation` asynchronously.
2. GIVEN an EventBridge rule is configured WHEN the event matches the rule pattern THEN Lambda SHALL be invoked within 1 second of the event being published.
3. GIVEN a Lambda invocation fails WHEN the error is retried THEN EventBridge SHALL retry up to 2 times with exponential backoff before sending to a Dead Letter Queue (DLQ) in SQS.

---

### R16 — Comunicar rezago de datos BCRA (1-2 meses)

**User Story:** As a Wayni user, I want to know that the BCRA data used in my evaluation may be 1–2 months old, so that I am not confused if recent payments don't seem to be reflected.

#### Acceptance Criteria

1. GIVEN a user views their Perfil Crediticio WHEN the explanation is rendered THEN it SHALL include a note about the BCRA data cutoff date, sourced from the `bcra_cutoff_date` field in DynamoDB.
2. GIVEN the `bcra_cutoff_date` is present WHEN the note is displayed THEN it SHALL be phrased in plain language (e.g., "The BCRA data used for your evaluation is from [date]. BCRA data is typically updated every 1–2 months.").
3. GIVEN `bcra_cutoff_date` is null or missing WHEN the profile is displayed THEN the system SHALL show a generic note ("BCRA data may have a 1–2 month delay") without surfacing the missing field as an error.

---

### R17 — Rechazados 1P y Renov bloqueados en v1 (assumption)

**User Story:** As a product manager, I want first-party rejected users and Renov users to be excluded from the credit profile feature in v1, so that we can focus on the validated use cases first.

#### Acceptance Criteria

1. GIVEN a user's `decision_state` is `1P_rejected` or `Renov_blocked` WHEN they call any Perfil Crediticio endpoint THEN the system SHALL return an HTTP 403 with a message indicating the feature is not yet available for their profile type.
2. GIVEN the exclusion logic is implemented in Lambda WHEN a new user type needs to be unblocked THEN it SHALL be configurable via an environment variable or DynamoDB flag without a Lambda redeployment.

> **Assumption**: Blocking 1P rejected and Renov users in v1 has no significant negative impact on retention. This must be validated with the Risk team.

---

### R18 — Validar costo de construcción y mantenimiento (gap)

**User Story:** As a finance stakeholder, I want to understand and monitor the ongoing AWS cost of the credit profile system, so that we can ensure it is economically viable.

#### Acceptance Criteria

1. GIVEN the system is deployed WHEN it is running in production THEN CloudWatch SHALL publish a `estimated_bedrock_cost_usd` custom metric updated daily, based on token usage logs.
2. GIVEN cost monitoring is active WHEN monthly Bedrock spend exceeds a defined threshold THEN a CloudWatch alarm SHALL notify the engineering and finance teams.
3. GIVEN the pre-calculation pattern (R4, R15) is in use WHEN explanations are pre-computed post-decision THEN the system SHALL avoid redundant Bedrock invocations by checking for a cached explanation in DynamoDB before invoking Bedrock.

> **Gap**: Full cost validation and ROI analysis deferred to a post-MVP phase.

---

### R19 — Validar ROI (gap)

**User Story:** As a business stakeholder, I want to measure whether the credit profile assistant actually reduces support queries, improves comprehension, and drives more retries and approvals, so that I can justify continued investment.

#### Acceptance Criteria

1. GIVEN the system is live WHEN users interact with the assistant THEN CloudWatch SHALL track the following KPI metrics: `support_deflection_rate`, `profile_views_total`, `assistant_sessions_total`, `dispute_flows_initiated`, `retry_date_shown_total`.
2. GIVEN KPI metrics are collected WHEN a CloudWatch dashboard is created THEN it SHALL visualize all 5 KPIs with daily granularity and a 30-day rolling window.
3. GIVEN the system has been live for 30 days WHEN a business review occurs THEN the team SHALL have access to enough data to evaluate whether the assistant is reducing support contacts (R13) and driving retries (R9).

> **Gap**: ROI validation (impact on approval rates, retention) deferred to post-MVP.
